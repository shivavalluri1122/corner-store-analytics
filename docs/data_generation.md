# Synthetic Data Generation Rules

Generated by `data/synthetic/generate_dataset.py`. Fully deterministic
(fixed seeds) so the same command always reproduces the same files.

## Coverage
- Date range: `2025-01-01` through `2025-12-31` (12 full months).
- Catalog: ~150 SKUs across 10 categories, defined in `sku_catalog.py`
  (deterministic prices/names, seeded).
- Store hours: 7am-9:59pm, with heavier weight at lunch (11am-1pm) and
  early evening (4pm-7pm).

## Seasonality rules
Applied as multipliers on the expected number of transactions per day
(actual count drawn from a Poisson distribution around that expectation):

| Rule | Multiplier | Where in code |
|---|---|---|
| Weekend lift (Fri/Sat/Sun higher than midweek) | Fri ×1.25, Sat ×1.45, Sun ×1.20, Mon/Thu ×1.0, Tue/Wed ×0.95 | `DOW_MULTIPLIER` |
| First-of-month spike (days 1-3) | ×1.4 | `FIRST_OF_MONTH_LIFT` |
| Mid-month spike (days 15-17) | ×1.25 | `MID_MONTH_LIFT` |
| Summer beverage lift (Jun/Jul/Aug) | ×1.6, applied only to the `Beverages` category's item-selection weight | `SUMMER_BEVERAGE_LIFT` |

First-of-month and mid-month multipliers are mutually exclusive per day
(first-of-month takes priority since it never overlaps mid-month days).

## Stockout gaps
5 SKUs are chosen at random (seeded) and each is assigned one contiguous
window of 7-21 days somewhere in the middle of the year. During its window,
that SKU is excluded from the item-selection pool entirely, producing a
visible zero-sales gap in `daily_item_sales` for that SKU — useful for
testing "out of stock" detection logic later.

## Transaction composition
- Number of transactions/day: `Poisson(base_rate × day_multiplier)`.
- Line items per transaction: 1-5, weighted toward 1-2 items
  (`ITEMS_PER_TXN_WEIGHTS`).
- Quantity per line item: 1-3, weighted toward 1 (`QTY_WEIGHTS`).
- SKU selection: weighted random draw using a per-SKU log-normal
  popularity weight (some items just sell more), with the summer lift
  applied on top for Beverages in summer months.
- ~6% of line items get a 10% discount.
- ~30% of transactions are tied to a loyalty customer (Faker-generated
  name/ID/reference) — the rest are anonymous walk-ins. This gives the
  Week 2 pipeline real PII to strip.

## Dataset sizing
- `large_clean.csv` (~50k rows) is generated directly at
  `base_transactions_per_day=60`.
- `small_clean.csv` (~2k rows) is **not** generated independently — it's a
  reproducible, date-stratified sample of whole transactions (never partial
  baskets) taken from `large_clean.csv`. Sampling whole transactions keeps
  every basket intact, and stratifying by date preserves the seasonality
  and stockout patterns at the smaller scale.
- `malformed.csv` (200 rows) starts from a slice of `small_clean.csv` and is
  corrupted afterward — see `docs/data_dictionary.md` for exactly what's
  broken and why.

## Regenerating the data
```
python -m data.synthetic.generate_dataset
```
`large_clean.csv` is gitignored (regeneratable); `small_clean.csv` and
`malformed.csv` are committed since they're small and used directly by
tests and the "Load Demo Store" button.
